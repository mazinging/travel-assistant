## 一、结论先行

| 维度 | 评价 |
|------|------|
| 架构设计 | ✅ ReAct + function calling 的选型合理，模型思考 / 代码执行 / prompt 承载业务规则的分工清晰 |
| 注释质量 | ✅ 注释解释"为什么"而非"是什么"，决策上下文保留完整，这在个人项目里很少见 |
| 正确性 | ❌ 有 4 处会产生**用户可见的错误结果**的缺陷（P0） |

| 工程化 | ❌ 无测试、无 lint、无结构化日志、无 CI，`.gitignore` 存在但仓库是否已初始化未知 |

## 二、P0：必须修的正确性缺陷（用户可见的错误结果）

这一节的问题和"代码风格"无关——它们会让用户拿到**错误的价格、或少住一晚、或看不到天气**，而且不会报错。

### P0-1 ⭐ `days=1` 时每天都被多算一晚酒店，却只查了 0 晚的房价

**位置**：`app/agents/planner.py:229-231`

```python
check_in = dep.isoformat()
hotel_nights = max(days - 1, 0)                                    # days=1 → 0
check_out = (dep + timedelta(days=max(days - 1, 1))).isoformat()   # days=1 → 出发日+1
return_date = (dep + timedelta(days=max(days - 1, 0))).isoformat()
```

**问题**：`check_out` 用的是 `max(days-1, 1)`，而 `hotel_nights` 用的是 `max(days-1, 0)`。两个 `max` 的下界不一致，导致 `days=1` 时：

- 系统告诉用户"**酒店住 0 晚**"
- 却拿着 `check_in=今天, check_out=明天` 去查**住 1 晚**的房价
- 模型拿到的价格是 1 晚的价，而 `nights` 字段被要求填 0
- 最终 `total_cost` 里的酒店项到底算没算，完全取决于模型怎么理解这条自相矛盾的输入

这**不是一个理论边界**：`PlanRequest` 允许 `days >= 1`，前端 `<input type="number" min="1">` 默认也允许 1。

**建议**：明确"1 天行程是否需要住宿"这一产品问题，然后让三个变量自洽。推荐做法——把语义显式化：

```python
hotel_nights = max(days - 1, 0)
check_in = dep.isoformat()
# 住 0 晚时 check_out 必须等于 check_in，否则数据源会按 1 晚计价
check_out = (dep + timedelta(days=hotel_nights)).isoformat() if hotel_nights else check_in
return_date = (dep + timedelta(days=max(days - 1, 0))).isoformat()
```

并在 `_meta.warnings` 里追加一句提示（当天往返无住宿）。

### P0-2 ⭐ 酒店**整晚数丢失**：`N 天行程实际需要 N-1 晚，但模型只看到单价**

**位置**：`app/services/tuniu.py:146-155` + `app/agents/planner.py:507-522`

```python
def _format_hotels(raw: dict) -> list[dict]:
    for h in items[:20]:
        out.append({
            "name": ..., "star": ..., "address": ..., "business": ...,
            "score": h.get("commentScore", ""),
            "price": h.get("lowestPrice", ""),      # ← 只给了「最低价」，没有任何计价口径
        })
```

**问题**：`lowestPrice` 是**单晚最低房价**，不含税、不含早、房型未知。把这个数字直接交给模型去乘 `nights` 得到 `hotel.total`，会系统性偏差：

1. 途牛返回的 `lowestPrice` 通常是**引流房型**（无窗/无早/不可取消），实际可订房型贵得多
2. 模型算 `total = price_per_night × nights` 时用的是这个引流价，用户按方案去下单会**价格对不上**
3. `_format_hotels` 扔掉了途牛返回里可能存在的 `lowestPrice` 之外的字段（含税价、房型名、是否含早），模型无从判断

**建议**（按成本从低到高）：

- **低成本**：把字段名从 `price` 改成 `price_per_night_from`，并在 `search_hotels` 的 tool description 里明确写"这是该酒店**最低房型**的单晚起步价，非最终成交价；方案里必须注明'起价，实际以预订页为准'"
- **中成本**：`_format_hotels` 保留更多原始字段（房型／含早／是否可取消），让模型有信息做取舍
- **高成本**：让途牛返回真实可订房型列表，取用户预算区间内**中位价**而非最低价

### P0-3 ⭐ 天气查询没有做日期对齐，跨月的行程**永远拿不到对应日期的天气**

**位置**：`app/agents/planner.py:267-271` + `app/services/weather.py:25`

```python
# planner.py
weather_list = await asyncio.to_thread(weather.get_weather, arrival_city, days)

# weather.py
for item in weather[: max(days, 1)]:   # ← 无条件取「未来第 1..days 天」
```

**问题**：`get_weather(city, days)` 返回的是**从今天起**的 `days` 天，它**完全不知道出发日期**。而：

- 用户通常提前 1~4 周做规划（`departure_date` 是未来日期）
- wttr.in 免费版只给 3 天预报
- 结果是：**一段与行程日期完全无关的天气**被贴到方案页面上，且没有任何提示

`README.md:61` 只说"旅行天数超过 3 天时只有前 3 天有准确天气"，但实际更糟：**天数 ≤ 3 时展示的也是今天的天气，不是出发日的天气**。

**建议**：

1. 在 `_format_day` 的返回值里已经带了 `date` 字段——用它和行程日期求交集：

```python
async def _attach_weather(result, arrival_city, dep, days):
    raw = await asyncio.to_thread(weather.get_weather, arrival_city, 3)
    trip_dates = {(dep + timedelta(days=i)).isoformat() for i in range(days)}
    matched = [w for w in raw if w.get("date") in trip_dates]
    result["weather"] = matched
    if len(matched) < days:
        result["_meta"]["warnings"].append(
            f"出发日 {dep} 超出天气预报范围（免费源仅提供未来 3 天），未提供天气信息"
        )
```

2. 前端 `renderWeather` 在 `list` 为空时不要静默 `innerHTML = ""`（见 P0-4），改为显示一行说明

### P0-4 ⭐ 天气失败被静默吞掉 + `_meta.warnings` 是死代码

**位置**：`app/agents/planner.py:267-283`

```python
weather_list = []
try:
    weather_list = await asyncio.to_thread(weather.get_weather, arrival_city, days)
except Exception:
    pass                        # ← 裸 except + pass，异常信息彻底丢失

result["weather"] = weather_list
result["_meta"] = {..., "warnings": []}   # ← 永远是空数组
```

**问题**：

- `except Exception: pass` 把网络错误、解析错误、城市名错误全部吞掉，**运维层面完全不可观测**
- 前端 `renderWeather([])` → `el.innerHTML = ""`，天气区块**整块消失**，用户不知道是"没数据"还是"页面坏了"
- `_meta.warnings` 声明了却从未写入——这是 v2 审查就已指出的问题，**至今仍是死代码**。它本该是承载"已知限制"（3 天预报、门票参考价、住 0 晚）的正确位置

**建议**：

```python
warnings: list[str] = []
try:
    weather_list = await asyncio.to_thread(weather.get_weather, arrival_city, 3)
except Exception as e:
    logger.warning("weather fetch failed city=%s err=%s", arrival_city, e)
    warnings.append(f"天气查询失败（{type(e).__name__}），方案中未含天气预报")
    weather_list = []
# ...然后按 P0-3 做日期对齐，不足的天数再追加一条 warning
```

前端配合改为：

```js
if (!list.length) {
  el.innerHTML = `<h2>🌤 天气</h2><div class="tips">暂无可用天气数据（可能出发日期超出预报范围）</div>`;
  return;
}
```

## 三、P1：健壮性与成本控制

### P1-1 没有总时长预算，最坏情况用户等 36 分钟

**位置**：`app/agents/planner.py:311-394`

`max_steps=24` 只管步数。每步一次 DeepSeek 调用（`timeout=90`），工具本身还有最大 30s 超时。理论上限：

```
24 步 × 90s(LLM) + N 次工具 × 30s ≈ 36 分钟以上
```

而**空响应重试分支与工具调用共享同一个 `max_steps`**（v2 审查已指出但未修）：如果模型持续返回空 `content`，代码会**空转满 24 次 LLM 调用**才抛错——这比旧版"第 1 步就失败"更费钱、更耗时。

**建议**（两处都改，成本极低）：

```python
async def _react_loop(messages, tuniu, max_steps=24, json_mode=False,
                      total_budget=180.0):
    empty_retries = 0
    async with asyncio.timeout(total_budget):     # Python 3.11+；3.10 用 wait_for
        for step in range(max_steps):
            ...
            if not content.strip():
                empty_retries += 1
                if empty_retries > 3:
                    raise RuntimeError("DeepSeek 连续多次返回空响应，已中止")
                continue
```

并在 `main.py` 捕获 `TimeoutError` → 返回 **HTTP 504 + 友好中文提示**，而不是 500 加一段英文堆栈。

### P1-2 工具串行执行，白等一半时间

**位置**：`app/agents/planner.py:376-391`

模型经常一次返回 3~5 个互不依赖的 `tool_call`（查车次 + 查酒店 + 查天气 + 搜景点）。当前 `for tc in tool_calls` 串行执行，每个都要等一次网络往返。

**注意**：`_ticket_cache` 是模块级 dict，并行后会有竞态（虽无害，但会有重复请求）。改成并行时顺手把缓存换成带锁的写法，或直接用 `functools.lru_cache` 包一层 `TuniuClient.search_tickets`。

```python
observations = await asyncio.gather(*[
    _execute_tool(tuniu, tc["function"]["name"], _safe_args(tc)) for tc in tool_calls
])
for tc, obs in zip(tool_calls, observations):
    messages.append({"role": "tool", "tool_call_id": tc.get("id", ""), "content": obs})
```

### P1-3 `_ticket_cache` 无上限、无 TTL

**位置**：`app/agents/planner.py:42`

```python
_ticket_cache: dict[str, str] = {}
```

模块级全局 dict，进程存活期间**只增不减**。多 worker（`uvicorn --workers 4`）下各 worker 各有一份，缓存命中率还被稀释。

**建议**：加一个有界 + TTL 的最小实现（无需引依赖）：

```python
from collections import OrderedDict
import time

class _TTLCache:
    def __init__(self, maxsize=256, ttl=1800):
        self._d, self.maxsize, self.ttl = OrderedDict(), maxsize, ttl
    def get(self, k):
        v = self._d.get(k)
        if not v: return None
        val, exp = v
        if exp < time.time():
            self._d.pop(k, None); return None
        self._d.move_to_end(k); return val
    def set(self, k, val):
        self._d[k] = (val, time.time() + self.ttl)
        self._d.move_to_end(k)
        while len(self._d) > self.maxsize:
            self._d.popitem(last=False)
```

### P1-4 外部 API 无重试、无限流退避

**位置**：`app/services/tuniu.py:70-78`、`app/services/deepseek.py:72-83`

三处都是"一次 `httpx.post`，非 200 就抛"。途牛门票接口在 `SYSTEM_PROMPT` 里被明确提到"有调用频率限制"，但**代码层没有任何退避重试**——它只是让模型"看到了错误自己想办法"。把限流处理寄托在 prompt 上，等于把可靠性交给了概率。

**建议**：给 `httpx` 加一个统一的重试装饰器（仅对幂等的 GET/查询类 POST 生效，429/5xx 退避）：

```python
async def _post_with_retry(url, *, retries=3, base=1.0, **kw):
    for i in range(retries):
        resp = await client.post(url, **kw)
        if resp.status_code == 429 or resp.status_code >= 500:
            await asyncio.sleep(base * 2 ** i)
            continue
        return resp
    return resp
```

### P1-5 同步路由 + `asyncio.run`，阻塞线程池且不可中断

**位置**：`app/main.py:36-65`、`app/agents/planner.py:186, 293`

```python
@app.post("/api/plan")
def api_plan(req: PlanRequest):        # 同步 def
    return planner.plan_trip(...)      # 内部 asyncio.run(...)
```

FastAPI 会把同步路由丢进 anyio 的线程池（默认 40 个线程），而每次请求内部用 `asyncio.run` **新建一个事件循环**。问题：

1. 线程池被长时间占满后，连 `/api/health` 都会排队
2. `asyncio.run` 创建的是**私有事件循环**，无法优雅取消；客户端断开后后端仍会烧完整个 ReAct 循环
3. 无法流式返回进度（用户面对一个转 3 分钟的 spinner）

**建议**：改成 `async def` + 直接 `await _plan_async(...)`。这不只是风格问题——它同时解锁了**流式进度**（SSE 推送"正在查车次…正在查酒店…"）和**客户端断开时取消**（`await request.is_disconnected()`）。

### P1-6 每次请求重新构造 `TuniuClient` / HTTP 连接

**位置**：`app/agents/planner.py:218, 301`

`TuniuClient(api_key)` 每次请求都新建，而 `httpx.post(...)` 是**模块级函数调用**，每次都新建连接、重新 TLS 握手。一轮 ReAct 里可能发起 10+ 次途牛请求，全部无法复用连接。

**建议**：`TuniuClient` 内部持有一个 `httpx.Client`（或在 FastAPI `lifespan` 里建全局 `httpx.AsyncClient`），连接池复用 + 统一超时配置。顺带解决 P1-4 的重试装饰器挂载点。

### P1-7 密钥缺失即全局 500，且 `ensure_keys` 逻辑过于粗暴

**位置**：`app/config.py:15-23`、`app/agents/planner.py:214-216, 298-300`

只要缺 `TAVILY_API_KEY`，**连"只查火车票"的规划请求也会 500**。健康检查已经把 `missing_keys` 暴露给前端了，但前端**从未调用** `/api/health`（`static/app.js` 里没有这段逻辑）——这个接口是死代码。

**建议**：

1. `ensure_keys()` 拆成 `required_keys()`（TUNIU + DEEPSEEK，真正必需）和 `optional_keys()`（TAVILY）
2. 可选 key 缺失时：在 `_execute_tool` 里让 `search_attractions` 返回 `{"error": "未配置 TAVILY_API_KEY，景点搜索不可用"}`，其余功能照常
3. 前端启动时调一次 `/api/health`，在页面上显示黄条提示，而不是等用户点提交才报错

### P1-8 无并发限制，单个用户可能打爆上游配额

**建议**：加一个 `asyncio.Semaphore(2)` 限制同时进行的 ReAct 循环数（`Depends` 或中间件），超出时返回 429 + "当前请求较多，请稍后重试"。对本地单用户工具是"以防万一"，但成本 3 行。

## 四、P2：正确性校验 —— 把 prompt 约束落成代码

### P2-1 所有硬约束都只写在 prompt 里，没有任何后置校验

`SYSTEM_PROMPT`（`planner.py:141-148`）明确要求：价格不得虚构、终点站不得是下辖县市、中转不得时间倒挂、指定时段不得出现凌晨车次、`total_cost` 公式固定。但**代码层零校验**。

后果是**静默错误**：模型违反约束时，用户看到的是一份看起来很合理、但事实错误的方案。这是当前架构最大的风险点。

**关键认识**：项目里**已经有** `_filter_trains_by_station` 和 `_extract_ticket` 两个"代码兜底"的先例——方向是对的，只是覆盖太少。应当沿着这条路继续。

**建议**：加一个 `_validate_plan(plan, ctx) -> list[str]`，在 `_plan_async` 返回前跑一遍，把问题写进 `_meta.warnings` 并回显到前端：

| 校验项 | 实现方式 | 不通过时 |
|--------|----------|----------|
| `total_cost` 公式 | `abs(total - (去+回+酒店+Σ门票)) < 1` | 用代码**重算并覆盖**，附 warning |
| 去程发车时段 | 从 `detail` 里正则抽 `\d{2}:\d{2}` 与用户需求比对 | warning："方案 X 发车时间可能不符合'9点左右'" |
| 中转时序 | 抽两段时间，比较先后 | warning 或**直接丢弃该方案** |
| 终点站在下辖县市 | 复用 `_filter_trains_by_station` 的白名单 | 直接丢弃该方案 |
| 价格是否为工具返回的真实值 | 记录每次工具返回的价格集合，方案里的价格必须命中 | warning："方案 X 的票价未在查询结果中找到" |
| 必需字段完整性 | Pydantic model 校验 `plans[*]` 结构 | 缺字段给默认值 + warning |

**"价格溯源"是投入产出比最高的一条**：在 `_execute_tool` 里维护一个 `known_prices: set[float]`，最终方案里每个价格必须能在集合里找到（或容差匹配）。这一条就能拦住模型最常见的"幻觉价格"。

### P2-2 `_parse_json` 无结构校验

**位置**：`app/agents/planner.py:572-592`

当前只保证"能解析成 dict"，不保证：

- 有 `plans` 键、是 list、非空
- 每个 plan 有 `outbound` / `return` / `hotel` / `tickets` / `itinerary` / `total_cost` / `reason`
- 数字字段真的是数字（模型经常输出 `"1200元"` 这种带单位的字符串）

前端 `renderPlans` 里已经有一堆 `p.hotel || {}`、`(p.tickets || []).map` 的防御式写法——**这些 `||` 就是在替后端擦屁股**。正确做法是后端用 Pydantic 定义 `TripPlan` / `PlanResponse`，解析后 `model_validate`，失败则带上原因重试一次（把校验错误回填给模型让它修正），仍失败才 500。

### P2-3 `_parse_json` 的"首 `{` 到末 `}`"截取法有已知破绽

**建议**：优先用 `json.JSONDecoder().raw_decode()` 从第一个 `{` 开始尝试解析，比字符串截取更鲁棒：

```python
decoder = json.JSONDecoder()
```

## 八、一个更根本的建议

当前架构的核心假设是：**"模型会遵守 prompt 里的硬约束"**。这个假设在 demo 阶段成立，在真实使用中不成立——`SYSTEM_PROMPT` 已经写了 8 条硬约束，越写越长，而模型对长约束的遵守率是**递减**的。

真正的解法不是继续往 prompt 里加规则，而是**把约束分层**：

```
第 1 层（代码强制）  —— 结构完整性、总价公式、价格溯源、站点白名单
                        ↑ 违反就拒绝或修正，不依赖模型
第 2 层（代码校验）  —— 发车时段、中转时序、预算区间
                        ↑ 违反不拒绝，但写进 warnings 展示给用户
第 3 层（prompt 引导）—— 路线合理性、推荐理由、个性化
                        ↑ 这个交给模型自由发挥，本来就是它的强项
```

项目里 `_filter_trains_by_station`（站点白名单）和 `_extract_ticket`（票种过滤）已经是第 1 层的雏形，说明这个方向是作者本来就想走的——只是**只走了两步就停了**。把第 1 层补齐，是让这个 Agent 从"能演示"变成"能信任"的关键一步。

### 10.1 P0-1 —— `days=1` 的住宿日期矛盾

**改动**：`app/agents/planner.py` 日期计算段

```python

return_date = (dep + timedelta(days=max(days - 1, 0))).isoformat()
```

**改动**：`_react_loop` 签名新增两个参数

```python
    json_mode: bool = False,
    total_budget: float = 180.0,      # 新增：墙上时间预算
```

## 十一、修复记录（v3.2）：输入校验与输出校验

本轮针对用户实测反馈的两类问题：**① 城市输入非法时的报错不可读；② 省份输入导致的
总价错误与时间线错乱。** 其中 ② 同时落地了第十节里建议的 P2-1。

### 11.1 根因诊断

两个现象看似无关，根因是同一个：**从用户输入到模型输出，全程没有任何校验。**

| 现象 | 实际链路 |
|------|----------|
| 乱码城市 → 直接报错 | 乱码穿透到 ReAct → 途牛返回空 → 模型无数据硬凑 或 烧完 24 步 → HTTP 500 + 上游错误原文 |
| 输入省份 → 总价错乱 | `_filter_trains_by_station("江苏")` 无站点以「江苏」开头 → **退回首列表** → 模型拿到南京/无锡/昆山混在一起的车次 → 编排出自相矛盾的方案 |
| 输入省份 → 时间线对不上 | 模型的 `itinerary` 从未被任何代码检查过 |

**注意第二条**：`_filter_trains_by_station` 的「过滤后为空则退回原列表」在 P0-2 里
被评价为「宁可放过不可错杀」的正确设计——**但在省份输入这个场景下，它恰恰是
错误的放大器**：退回的是一份跨越多城市的杂乱列表，模型据此编排必然出错。
这是「同一个兜底策略在不同上下文下效果相反」的典型案例。

### 11.2 新增 `app/services/city.py`：输入校验

三种输入分类处理：

| 输入 | 判定 | 行为 |
|------|------|------|
| 苏州 / 北京市 / 苏州站 | `ok` | 归一化为「苏州」后正常规划 |
| 江苏 / 新疆 / 内蒙古 | `province` | 返回候选城市列表，**不报错** |
| asdfgh / ????? / 空 | `invalid` | 立即提示「请填写中文城市名」 |

设计要点：

1. **省份不是错误**，是「用户没说清楚」。所以用 **409 Conflict + 候选列表**，
   而不是 400 报错——语义准确，前端也能据此弹出选择而非显示错误。
2. **归一化必须回写**。`_validate_cities` 返回归一化后的三元组，调用方**必须使用返回值**，
   否则「苏州市」会带着后缀传给途牛导致查不到。
3. **中文地名放行**。内置表不可能穷举全国县市，`_looks_like_chinese_place` 
   （2-8 个汉字）用于拦截**乱码**，而不是做精确地理校验——否则用户查个小县城会被误拦。
   表外中文地名照常放行，真正的「不存在」由数据源在下游暴露。
4. **零网络开销**：纯本地判断，挡在 ReAct 之前，每次规划都能跑，不消耗任何 API 配额。

### 11.3 新增输出校验：`_fix_total_cost` + `_check_itinerary`

这是第十节建议的 P2-1 的落地。核心原则：**编排交给模型，算数和时序交给代码。**

**`_fix_total_cost`** —— 重算而非相信：

```python
expected = 去程 price + 回程 price + hotel.total + Σ门票 price
if abs(actual - expected) > 1:
    plan["total_cost"] = expected      # 直接覆盖，并记一条 warning
```

- 容忍 `"700"` 这种字符串数字
- 数据缺失严重（连车票都没有）时**不硬算**，避免产出更误导的数字
- 免费门票（`price: null`）按 0 计入

**`_check_itinerary`** —— 四项确定性检查：

| 检查 | 判定方式 |
|------|----------|
| 行程天数与要求一致 | `len(itinerary) != days` |
| 日程序号连续 | `sorted(day_nums) != range(1, n+1)` |
| 时间倒挂 | 正则抽 `HH:MM` 比较去程/回程 |
| 日程日期越界 | 是否落在 `[出发日, 回程日]` 内 |

注意 `_extract_first_time` 的做法：模型的 `detail` 是自由文本，
**不解析语义，只提取可验证的片段**（`\b([01]?\d|2[0-3]):([0-5]\d)\b`）。
这是「模型输出不可信」场景下的通用手法——能验证多少就验证多少。

所有问题写入 `_meta.warnings`，由前端「请注意」区展示；**正确的部分静默通过**，
不打扰用户。

### 11.4 前端：省份 → 城市选择器

新增 `#city-picker` 区块与 `PlanError` 类。收到 409 时：

1. 解析 `detail.field` 判断是哪个字段（出发/目的地/中转）
2. 渲染候选城市为可点按钮
3. 点击后替换该字段、回写表单、**自动重新提交**

用户不必重填整个表单。样式用蓝色（`border-left: 4px solid var(--primary)`）
而非红/黄色——这不是错误。

## 十二、修复记录（v3.3）：输入关系校验与市内游

### 12.1 问题：同城 + 1 天导致的「沉默错误链」

用户实测：出发城市 = 目的地城市（如都填"南京"）、天数 = 1 时，产出的方案有问题。

**根因不是某个 bug，而是三个漏洞同时作用：**

| # | 漏洞 | 后果 |
|---|------|------|
| 1 | 没有任何代码检查「出发地 = 目的地」 | 两个城市各自合法，组合起来无意义 |
| 2 | 模型按指令查「南京→南京」车次 → 途牛返回**空列表** | 空列表不是异常，`_execute_tool` 正常返回 `[]`，**没有任何错误信号** |
| 3 | 后端三个校验器全部放行 | 总价：车票缺失→按设计跳过；时间线：天数对得上→通过；天气：正常 |

**模型拿到空数据但必须交差 → 硬凑方案 → 用户拿到一份没有真实交通依据、
但看起来正常的方案。**

这是「沉默错误链」的教科书案例：**每一环单独看都正确，合起来产出坏结果。**

注意第 2 条与第 11 节那个「省份导致 `or trains` 放大错误」是**同源问题**：
都是「空结果没有产生任何错误信号，于是被当成正常数据继续处理」。

### 12.2 修复：分两种情况处理

**产品决定（用户选择）：市内游是合理需求，允许，但要明确提示。**

因此不做「一律报错」，而是**改变告知模型的内容**：

```python
same_city = _detect_same_city(departure_city, arrival_city)
# user 消息里追加：
if same_city:
    trip_hint = ("⚠️ 本次是【市内游】：出发地和目的地都是 X，"
                 "不需要查询城际火车票，outbound/return 的 price 都填 0……")
```

**为什么改 user 消息而不是改工具**：市内游与城际游的差别只在「要不要查车次」，
把这一点直接告诉模型，成本最低且不需要动任何工具代码。

配套三处：
1. `SYSTEM_PROMPT` 新增一条硬约束（识别【市内游】标记 → 不查车次、price 填 0）
2. `_meta.warnings` 加一条用户可见提示
3. 提示里包含"若这不是你的本意，请修改出发地或目的地"——**因为填错的可能性很大**

### 12.3 新增 `_validate_trip_inputs`：字段**关系**校验

这是本项目第一次做「关系校验」（此前全是单字段校验）。

| 检查 | 处理 | 理由 |
|------|------|------|
| 出发地 = 目的地 | **放行** + 提示 | 市内游是合理需求 |
| 中转城市 = 出发地/目的地 | **400 报错** | 逻辑无解，没有合理降级方式 |
| 出发日期在过去 | **400 报错** | 查不到任何数据，只会让模型硬凑 |

新增 `InvalidTripError(ValueError)` —— 继承 `ValueError` 使 `main.py` 的
「ValueError → 400」映射自动生效；与 `InvalidCityError` 分开是因为语义不同：
一个是"字段填错了"，一个是"字段组合起来没意义"。

### 12.4 一个可以带走的规律

> **单字段校验永远抓不到「组合无意义」的输入。**

此类输入的特征是：**每个字段单独看都合法，格式全对，但语义矛盾。**

值得警惕的同类组合（本项目已处理前三个）：

| 组合 | 状态 |
|------|------|
| 出发地 = 目的地 | ✅ 已处理（市内游） |
| 中转 = 出发地 / 目的地 | ✅ 已处理（报错） |
| 日期在过去 | ✅ 已处理（报错） |
| 1 天行程 + 要求「住五星酒店」 | ⬜ 未处理（需求冲突） |
| 30 天行程 + 天气只有 3 天 | ✅ 已处理（warning） |

**这类问题只能靠"撞"出来，不能靠"设计"出来**——但每撞到一次，
就应该问一句：**"还有哪些字段组合会无意义？"**
