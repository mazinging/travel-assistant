# 用轨迹学习 Agent —— 观察指南

> 这份文档不是讲"怎么用功能"，而是讲**怎么用这些数据理解 agent**。
> 代码在 `app/agents/trace.py`，面板在页面底部「🔍 Agent 执行轨迹」。

---

## 一、为什么需要它

传统程序：读代码 → 理解逻辑 → 学会了。

**Agent 不行**，因为 agent 的行为不是代码决定的，是模型在**运行时**决定的。
读 `_react_loop` 你只能知道"可能的路径"，不可能知道"实际走了哪条"。

下面这些问题，**读代码一个都答不出来**：

| 问题 | 为什么读代码答不出来 |
|------|---------------------|
| 模型按什么顺序查数据？ | 顺序由模型决定，代码里没有 |
| 平均跑几轮循环？ | 取决于模型判断，代码只给了上限 |
| prompt_tokens 涨到多少？ | 取决于每轮 observation 的实际大小 |
| 哪个工具经常失败？ | 取决于外部 API 的真实状态 |
| 我加的校验器触发了几次？ | 取决于模型实际输出了什么 |

**这些都是 agent 工程最核心的问题，而它们只能通过观察得到答案。**

## 二、面板里每个数字该问什么问题

### 汇总区

```
2 轮 LLM 调用 · 3 次工具调用 · 失败 0 次 · 空响应重试 0 次
累计 7,100 输入 tokens + 210 输出 tokens · 总耗时 5.9s
最终上下文 9 条消息
每轮输入 tokens：2,500 → 4,600
```

| 字段 | 该问的问题 | 可能的意义 |
|------|-----------|-----------|
| `llm_rounds` | 实际几轮？离 `max_steps=24` 有多远？ | 若总在 2-3 轮，说明安全阀开得过大 |
| `tool_calls` | 一共查了几次？ | 对比轮数看并行度 |
| `tool_errors` | 失败率多高？ | 高 → 外部 API 不稳，或参数传错 |
| `empty_retries` | 模型健康度 | >0 → 模型有截断/异常问题 |
| `prompt_tokens_total` | 一次规划的真实成本 | 换算成钱就是单次开销 |
| `prompt_tokens_growth` | **最重要的一个** | 见下节 |
| `final_message_count` | 上下文规模 | 涨太快说明该做 context 压缩 |

### `prompt_tokens_growth` —— 直接看见 ReAct 的成本特征

这是数组，每轮一个数。**连续看它，就是在看 ReAct 的成本曲线。**

因为每一轮都要**重发全部历史**，所以：

```
第 1 轮：2,500   ← system prompt + 用户输入
第 2 轮：4,600   ← 上面那些 + 第 1 轮的 observation
第 3 轮：6,800   ← 再加第 2 轮的
第 5 轮：11,000  ← 大部分是重复内容
```

**每一轮的增长量 ≈ 上一轮新增的 observation 大小。**

N 轮的总消耗 ≈ O(N²) —— 这就是为什么工业界的 agent 都要做
context 管理（摘要、只留最近 N 轮、压缩 observation）。

**你现在可以直接验证这个说法，而不是相信我。**

### 工具表

```
工具              调用  失败  耗时
search_trains      1     0    800 ms
search_hotels      1     0    600 ms
search_tickets     1     1    200 ms   ← 红色
```

| 观察点 | 说明 |
|--------|------|
| 哪个工具最慢？ | 串行执行时，它是瓶颈；并行能省多少？ |
| 失败的那个 | 点开原始记录看 `error_msg`，是限流还是参数错？ |
| 同一工具被调多次？ | 说明模型在重复查询（缓存或 prompt 的问题） |

### 原始记录（逐行）

```
#0  search_trains   {"departure_city":"合肥","arrival_city":"苏州"}   800ms · 1800字符
#0  search_hotels   {"city":"苏州","check_in":"2025-12-01"}          600ms · 900字符
#1  search_tickets  {"scenic_name":"拙政园"}                         200ms · 60字符  ERROR
```

**这一行行的东西就是 ReAct 的"思考→行动→观察"轨迹本身。**

特别值得看的：
- `args` —— 模型传的参数对不对？有没有编造日期、传错城市名？
- 同一个 `step` 出现多行 —— 模型在**并行请求**多个工具（可优化为真并行）
- `observation_chars` 特别大的 —— context 膨胀的主因

## 三、四个实验（每个 5 分钟）

有了轨迹，就可以做实验了。**这才是学 agent 最有效的方法。**

### 实验 A：`max_steps` 到底该设多少

```python
# planner.py: _react_loop(max_steps=24)
```

改成 `8`，再改成 `4`，各跑几次，对比轨迹里的 `llm_rounds`。

**观察**：模型会提前放弃吗？输出质量下降吗？还是根本用不到？

**学到**：`max_steps` 的真实作用。现在这个 24 是拍脑袋定的，
**轨迹会告诉你它其实从来没有被接近过（或者经常撞上）**。

### 实验 B：9 条 prompt 约束，哪几条真的有用

`SYSTEM_PROMPT` 的硬约束是历史累积的，**没有一条被验证过**。

把它们砍到 3 条（只留"价格不得虚构""终点站校验""指定时段"），跑几次对比。

**观察**：输出质量真的下降吗？下降在哪？

**学到**：prompt 里的规则到底有几条在起作用。这是 prompt 工程最核心的问题，
而你有个绝佳的实验场。

### 实验 C：`_filter_trains_by_station` 是不是必需的

把它临时改成 `return trains`（不过滤），跑几次。

**观察**：模型能自己识别"张家港不是苏州"吗？

**学到**：**哪些事模型真的做不了、必须代码兜底**。

两种结果都有价值：
- 模型能处理 → 这个函数不必要，可以删
- 模型完全不行 → 这个函数是必需的，且你理解了为什么

### 实验 D：observation 大小如何影响表现

```python
# _execute_tool 里
trains[:20]  →  trains[:5]  →  trains[:40]
```

**观察**：决策质量 vs token 成本。看 `prompt_tokens_growth` 和最终方案质量。

**学到**：**observation 大小是 agent 的核心权衡**——给太少模型信息不足，
给太多烧钱且可能淹没重点。

## 四、一个具体的观察任务

跑 5 次不同城市/天数的规划，记录每次的：

```
城市对          轮数  工具调用  prompt总tokens  失败  耗时
合肥→苏州 3天    ?     ?         ?               ?     ?
北京→上海 2天    ?     ?         ?               ?     ?
...
```

然后回答：

1. **调用顺序是否每次相同？** 如果都是"车次→酒店→天气→景点"，
   说明 `/api/plan` 这条路径**根本不需要 ReAct**——固定流水线更可靠更便宜。
   这是个重要的架构判断，而**只有数据能证明它**。
2. **轮数和城市/天数相关吗？** 复杂的行程需要更多轮吗？
3. **有没有哪个工具总是失败？**
4. **校验器（总价/时间线）触发了几次？** 触发多说明模型算术不行；
   触发少说明这些校验是"保险"而非"修复"。

**第 1 条如果成立，是这次学习最大的收获。**

## 五、用轨迹排查真实 bug

轨迹不只是"学习工具"，也是**排查工具**。

比如已知的一个缺陷：`_check_itinerary` 的时间倒挂检查**会误报**——
它比较去程和回程的第一个 `HH:MM`，但没考虑**跨天**。

```
去程 09:15 出发（第 1 天）
回程 08:00 出发（第 3 天）  ← 正常！
→ ret_t("08:00") < out_t("09:15") → 误报"时间倒挂"
```

**用轨迹可以确认这个判断**：

1. 跑几次真实规划
2. 看 `summary` 里有没有"时间倒挂"的 warning
3. 如果有，对照轨迹里的 `search_trains` 参数和方案内容
4. 确认：这是误报吗？触发条件是什么？

**然后你才动手修** —— 而不是凭推测修。

这就是我在前面几轮反复强调的：
**agent 工程里，判断应该来自观察，不是来自推理。**

---

## 六、注意：轨迹本身也有成本

`_meta.trace` 会随响应返回。`prompt_tokens_growth` 这类是常数大小，
但 `tool_calls` 里的 `args` 和 `error_msg` 会随工具调用次数增长。

对本地工具这完全不是问题（走 localhost）。但要知道这个权衡：
**观测性总是有代价的**，生产环境通常会用采样率或只保留汇总来控制。
